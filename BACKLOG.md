# LearnBox release backlog

**Status:** Web/PWA v1 is LIVE and CLOSED (2026-09-28, Production application SHA `2acdcef4`),
recorded as annotated tag `v1.0.0` and a GitHub Release. The repository is **private** by security
decision (LB-B10 containment).
This document is the authoritative backlog and v1.1 candidate boundary.

**Scope planning:** a decision-support deep-dive of all 21 items, with three v1.1 scope options
and a recommendation, is recorded as a planning snapshot in
[`docs/planning/V1_1_SCOPE_ANALYSIS.md`](docs/planning/V1_1_SCOPE_ANALYSIS.md). That document is
analysis only; this file remains the authoritative backlog.

Priority is planning input, not authorization to work. Nothing here is approved for implementation
until the owner selects the v1.1 scope. Effort is deliberately not estimated.

**Confidence vocabulary:** `PROVEN` (verified against live Production or repository evidence during
the 2026-09-28 audit), `LIKELY` (strong documentary evidence, not directly exercised), `UNCERTAIN`
(needs investigation before planning).

## v1.1 candidate boundary

Proposed as a coherent, limited maintenance and trust release — not a return to broad feature
development. The owner selects the final scope.

**Strong v1.1 candidates**

- LB-B01 automated database backups — recurring recovery point for live learner data.
- LB-B02 monitoring and alerting — detect failure without waiting for a user report.
- LB-B04 account deletion, privacy notice and support route — release-critical surfaces the
  roadmap required for v1.0 and the live product shipped without.
- LB-B03 activate the Profile identity read — small, flag-gated, completes the Profile surface.
- LB-B07 + LB-B08 OTP delivery resilience — a real sign-in failure mode with no user recourse.
- LB-B14 accessibility sweep — the public product has no exercised accessibility evidence.
- LB-B09 reconcile the canonical manifest with the activated state.
- LB-B21 finish documentation closure in secondary documents.

**Better deferred**

- LB-B12, LB-B15, LB-B16, LB-B17, LB-B18, LB-B19, LB-B20 — platform expansion, commerce and
  AI-factory work already excluded from v1.0; no current evidence supports reconsidering them.
- LB-B11 server-backed progress — meaningful but larger; sequence after the trust items.

**Investigation required before planning**

- LB-B05 synthetic audio — decide whether native-speaker recording is a v1.1 goal, and resolve
  the two recorded transcription discrepancies. Depends on a content/budget decision.
- LB-B06 media out of the application image — depends on the storage decision below.
- LB-B13 Admin operations — scope depends on whether support tooling is needed before growth.

## Owner decisions required

1. **v1.1 scope selection** from the candidate set above; nothing is authorized until then.
2. **Private media storage** — keep media in the application image (LB-B06) or move to object
   storage. This gates the content release model and interacts with LB-B10.
3. **Media in Git history** (LB-B10 follow-up) — resolved for anonymous access: the repository is
   now private. Still open: whether to remove the media blobs from Git history and serve media only
   through the authenticated route, or to accept that anyone with repository access can retrieve
   them. History rewriting is destructive and must not be attempted without explicit owner
   authorization. This interacts with decision 2.
4. **Audio quality** (LB-B05) — accept the owner-approved synthetic set for v1.1, or fund native
   recording.
5. **Backup retention and cost** (LB-B01) — frequency and retention window for the live database.

**LB-B11 root cause established (2026-09-29, read-only investigation).** The reported "progress
resets to zero after re-login" is **not** data loss and **not** an identity defect. Production data
is intact and per-user, and `ON CONFLICT (phone_e164) … RETURNING id` returns a stable user id. Two
defects combine: the home screen reads daily count and streak only from device storage
(`packages/learning-engine` performs no network calls), while `/api/learner/progress` is correct but
consumed only by the progress screen; and the device storage scope collapses to
`:account:unverified` when the session expires, so a stale scope renders as zero. No migration and

### Residual risks carried out of v1.1

1. **Recurring restore is still unproven.** The scheduled backup now has a real execution behind
   it (`2026-09-29 02:31:01 UTC`, 36 tables, verified archive), but the weekly restore drill has
   never fired; it is proven only by a manual run. Backups that are never restored on schedule are
   an assumption about recovery, not evidence of it. An enabled timer and a green `Result` are
   both defaults for a unit that never started and must not be counted as a successful run.
2. **Recovery depends on artifacts that must not be deleted** — the pre-migration dump, the
   `.env` backup, the rollback image `rollback-pre-v110-2acdcef4` and the non-expiring Neon branch.
   Removing any of them without a replacement removes the ability to roll back.
3. **Single-host Production.** One VPS runs Caddy and every application container; there is no
   redundancy and no failover. Restart is self-healing, silent degradation is not.
4. **The learner base is very small** (2 real accounts). Conclusions about load, retention or
   scheduling behaviour drawn from current data are weak evidence.
5. **Deletion does not immediately purge backups.** A deleted learner's data persists in existing
   backups until those backups age out. The privacy notice states this; retention is 30 days.
6. **OTP delivery depends on a single provider** (SMS.ir) with a finite balance. The support bot is
   the only escape path when delivery fails.
7. **Provenance is only as good as the build path.** Images are built on the Production host from a
   verified archive because the host cannot fetch the private repository. The `APP_SOURCE_SHA`
   label makes the result auditable, but the build is not reproducible from CI.
