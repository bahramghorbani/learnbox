## ۳. طبقه‌بندی مسائل باقی‌مانده

### P0 — مانع استقرار امن

1. **migrationهای ۰۰۲۴ تا ۰۰۳۴ روی Production اعمال نشده‌اند.** Admin امروز به
   `store_listings`، `purchase_events`، `users.status`، `presentation_slides` و grantهای
   مدیریت محتوا تکیه می‌کند. استقرار کد روی schema فعلی Production یعنی خطای ۵۰۰ در چند
   کارگاه. ترتیب و بازگشت‌پذیری هر migration باید پیش از استقرار جداگانه تأیید شود.
2. **کسری grant در ۰۰۲۶ و ۰۰۲۷.** این دو migration هیچ grant ای برای نقش `learnbox_admin`
   اضافه نمی‌کنند؛ زیر نقش‌های کم‌امتیاز، خواندن `store_listings` و `purchase_events` شکست
   می‌خورد. باید پیش از استقرار جبران شود.

### P1 — مانع کار عادی Admin

3. **ذخیره‌سازی رسانهٔ خصوصی انتخاب نشده (LB-B56).** جایگزینی اسپلش و رسانهٔ اسلاید به یک
   مقصد ذخیره‌سازی جداشده نیاز دارد که مالک هنوز انتخاب نکرده است.
4. **هیچ تأیید واقعی کاربر روی Production نیست.** همهٔ تأییدها روی dev و CI هستند؛ هیچ
   اپراتور واقعی با Passkey واقعی روی دامنهٔ Production این UI را ندیده است.

### P2 — مهم ولی بازدارنده نیست

5. **LB-B58** — مرز روز فیلتر Audit (بالا).
6. **LB-B55** — مدل خواندن توزیع پیشرفت یادگیری هنوز تأیید نشده؛ کارگاه یادگیری تا آن زمان
   محدود می‌ماند.
7. **LB-B57** — هیچ مدل سلامت سرویس یا وضعیت اجرا تأیید نشده؛ کارگاه عملیات آن کارت‌ها را
   «در دسترس نیست» نشان می‌دهد و هرگز عدد نمی‌سازد.

### P3 — ظاهری یا آینده

8. **LB-B59** — گیت خودکار واکنش‌گرایی/دسترس‌پذیری در CI.
9. **LB-B42** — کنترل‌های هدر (جست‌وجوی ⌘K، زنگ اعلان، چیپ کاربر) backend ندارند.
10. **LB-B43** — نوع کارت نوار کناری Bobo منتظر تصمیم مالک و یک منبع واقعی نسخه/سلامت است.
11. **LB-B49** — تصویر جلد فروشگاه به endpoint ای با URL امضاشده نیاز دارد.
12. **LB-B50 / LB-B54** — prototype نه `review.html` دارد و نه جای ناوبری برای بازبینی؛ هر دو
    اصلاحیهٔ PDR-009 می‌خواهند، نه کد.

## ۶. وابستگی‌های ذخیره‌سازی

- جایگزینی اسپلش و رسانهٔ اسلاید به ذخیره‌سازی خصوصی جداشده نیاز دارند (LB-B56، باز).

- تا آن زمان این سطح‌ها حالت «در دسترس نیست» نشان می‌دهند و عدد یا تصویر جعلی نمی‌سازند.

## ۷. پیش‌نیازهای بازگشت

1. هر مرحله یک squash commit مستقل است؛ `git revert <sha>` کافی است.
2. digest فعلی Production (`sha256:20263ce025b2…`) باید پیش از استقرار یادداشت شود تا
   بازگشت فقط یک redeploy همان digest باشد.
3. migrationها پیش از کد اعمال می‌شوند و باید جداگانه بازگشت‌پذیر باشند؛ هیچ migration ای
   در این مجموعه مراحل اعمال نشده است.
4. learner با compose جدا مستقر می‌شود و در هیچ سناریوی بازگشتی لمس نمی‌شود.

## ۸. آزمون دود پس از استقرار (لازم)

1. ورود با Passkey واقعی روی دامنهٔ Production.
2. انقضای نشست و سیاست بازاحراز پنج‌دقیقه‌ای: یک عمل حساس باید ۴۲۸ بگیرد و پس از بازاحراز
   موفق شود.
3. هر ۹ مقصد ناوبری باز شود بدون ۵۰۰ و بدون صفحهٔ خالی.
4. داشبورد اعداد واقعی نشان دهد یا «در دسترس نیست» — هیچ عدد بی‌منبع.
5. مشاهدهٔ Audit log و ثبت‌شدن همین نشست در آن.
6. یک چرخهٔ کامل بسته: ساخت پیش‌نویس، بازبینی، انتشار — سپس بازگشت وضعیت.
7. فروشگاه و تراکنش‌ها بارگذاری شوند بدون فعال‌شدن هیچ درگاه پرداختی.
8. عرض موبایل روی یک دستگاه واقعی: ناوبری قابل رسیدن، بدون سرریز افقی.

## ۹. ارزیابی

کد Admin از نظر UI، دسترس‌پذیری و رگرسیون در وضعیت قابل‌استقرار است. آنچه مانع است کد نیست:
**schema و grantهای Production (P0)**، و **انتخاب ذخیره‌سازی خصوصی (P1)**. تا اعمال و تأیید
migrationهای ۰۰۲۴ تا ۰۰۳۴ همراه با جبران grantهای ۰۰۲۶/۰۰۲۷، استقرار Production امن نیست.
