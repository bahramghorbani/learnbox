# برنامهٔ اجرایی پیاده‌سازی طراحی تأییدشدهٔ Admin

- **طراحی مرجع:** `prototypes/admin-ui-v1` روی branch `proto/admin-ui-concept`، کامیت `8b3e050d`.
- **مجوز طراحی:** `docs/product-decisions/PDR-009-ADMIN-UI-DESIGN-FREEZE-AND-BOBO-VARIANTS.md`
  (approved, design frozen).
- **وضعیت این سند:** برنامه است، نه پیاده‌سازی. هیچ مرحله‌ای بدون دستور مالک آغاز نمی‌شود.
- **قاعدهٔ حاکم:** اجرای دقیق طراحی تأییدشده روی Backend موجود. بازنویسی سیستم، طراحی سلیقه‌ای
  جایگزین، و حذف قابلیت موجود ممنوع است.

## قواعد غیرقابل‌مذاکره برای همهٔ مراحل

1. branch طراحی مستقیماً در `main` ادغام نمی‌شود؛ فقط به‌عنوان مرجع بصری خوانده می‌شود.
2. دادهٔ نمایشی prototype (`assets/js/data.js`) هرگز وارد کد محصول نمی‌شود. هر عددی که در UI دیده
   می‌شود باید از API واقعی Admin بیاید.
3. دادهٔ بدون منبع واقعی «در دسترس نیست» نشان داده می‌شود، نه عدد ساختگی (قاعدهٔ `empty.html`).
4. هیچ منطق امنیتی یا تجاری به‌خاطر ظاهر حذف یا تضعیف نمی‌شود: Passkey، سیاست reauth پنج‌دقیقه‌ای،
   محدودیت `is_free`/`price_tomans`، نقش‌ها و مرز دادهٔ زبان‌آموز دست‌نخورده می‌مانند.
5. قابلیت‌های امروز Admin حتی اگر در prototype دیده نشوند حفظ می‌شوند (فهرست در بخش «موجودی»).
6. هر مرحله یک PR مستقل، با CI الزامی سبز، و قابل بازگشت با revert همان PR.
7. استقرار Production فقط با مجوز مالک و فقط Admin؛ learner در هیچ مرحله‌ای redeploy نمی‌شود.

> می‌ماند. بنابراین بازبینی مقصد `#review` خودش را گرفت و از پنل «بسته‌های جدید و در حال بررسی»
> روی داشبورد — همان پنلی که عمق صفش را نشان می‌دهد — قابل دسترسی است.
>
> آنچه ساخته شد:
>
> - `DashboardWorkspace` روی پوستهٔ `admin-shell cp-workspace` + `page-head`؛ شش کارت `kpi`، سه
>   نمودار، پنج `qa` اقدام سریع و سه پنل `card` — دقیقاً ترکیب‌بندی و کلاس‌های `index.html` منجمد.

>   `LEARNBOX_ADMIN_DASHBOARD_ENABLED` + runtime گذرکلید؛ نقش‌های خوانندهٔ عملیاتی
>   (`content_reviewer` / `content_publisher` / `super_admin`) روی store بررسی می‌شوند و نبودِ نقش
>   ۴۰۴ می‌دهد نه ۴۰۳.
> - نمودارها SVG درون‌خطی با همان هندسهٔ `areaChart`/`barChart`/`donut` مرجع‌اند؛ هیچ کتابخانهٔ
>   نمودار به bundle اضافه نشد.
>
> **قاعدهٔ معماری که CI گرفت (و درست گرفت):** نسخهٔ اول این مرحله یک donut از توزیع
> `card_schedules.state` می‌کشید و روزها را با `date_trunc('day', …)` سطل‌بندی می‌کرد. گیت‌های
> LB-B35 CP2 در `apps/website/test/cp2-no-redefinition-guard.test.ts` و
> `cp0-learning-db-characterization.test.ts` هر دو را رد کردند: **هیچ لایه‌ای بیرون از
> `packages/learning-engine` اجازه ندارد وضعیت scheduler یا «روز یادگیری» را نام ببرد یا بازتعریف
> کند، و Admin حتی اجازهٔ import آن پکیج را هم ندارد.** این گیت ضعیف نشد؛ کد اصلاح شد:
>
> - donut سوم از `card_schedules.state` به `card_versions.status` (enum `content_status`، مهاجرت
>   `0003`) منتقل شد — یعنی «وضعیت خط تولید محتوا»، همان دامنه‌ای که Admin واقعاً اداره می‌کند.
>   Admin دیگر هیچ واژهٔ وضعیت scheduler ندارد.
> - سطل‌بندی روز از SQL برداشته شد: مرزهای ۳۱گانهٔ نیمه‌شب یک‌بار با `Intl` در منطقهٔ گزارش‌دهی
>   حساب می‌شوند و PostgreSQL فقط با `width_bucket` می‌گوید هر رکورد در کدام سطل افتاده. سری
>   خروجی چگال است، پس روز بدون داده صفرِ واقعی است نه روزِ گم‌شده.
> - `admin-dashboard-grants.test.ts` همین قاعده را محلی هم pin می‌کند (`card_schedules`،
>   `date_trunc`، import موتور و واژگان scheduler همه ممنوع) تا بازگشت drift در CI لو برود.
> - `fa-dates.ts` مشترک (`faDay`/`faDateTime`/`faRelative`) با `Intl` — بدون کتابخانهٔ تاریخ و بدون

  ورود دوباره — **بدون** کاهش پنجرهٔ پنج‌دقیقه‌ای و بدون ایجاد مسیر دور زدن Passkey.
- **وابستگی:** مرحلهٔ ۱.
- **معیار پذیرش:** نشست منقضی پیام روشن و مسیر بازیابی می‌گیرد؛ نشست معتبر رفتار امروز را دارد؛
  `BOOTSTRAP_ENABLED=false` و الزام Passkey دست‌نخورده؛ تست منفی برای تلاش بدون احراز هویت.
- **تست:** تست مسیر نشست منقضی/معتبر/بدون نشست؛ اجرای verifier امنیتی وب.
- **خطر:** این حساس‌ترین مرحله است — هر اشتباهی مرز احراز هویت را تضعیف می‌کند. **کاهش:** تست منفی
  اجباری، بازبینی مستقل، و استقرار جداگانه از بقیهٔ مراحل. **بازگشت:** revert PR و استقرار image قبلی.

#### اجرای مرحلهٔ ۸ (candidate؛ در انتظار PR و CI)

- `#access` اکنون یک مقصد واقعی است و فقط قراردادهای بالفعل را نمایش می‌دهد: وضعیت همین نشست و
  وضعیت تازگی احراز هویت از `GET /api/auth/session`، و ثبت Passkey تازه از مسیر موجود. هیچ فهرست
  ساختگی دستگاه، نشست، نقش یا رویداد امنیتی از prototype وارد نشده است؛ نبودِ API مربوط با empty
  state صریح نشان داده می‌شود.
- `AdminAuthGate` اکنون ۴۰۱ (نیاز به ورود با Passkey) را از خطای سرویس/شبکه جدا می‌کند؛ خطای سرویس
  دکمهٔ تلاش دوباره می‌دهد و هرگز به اشتباه صفحهٔ ورود را نمایش نمی‌دهد.
- ثبت Passkey جدید اکنون server-side به احراز هویت تازه گره خورده است: routes options و verify هر دو
  `428 no-store` می‌دهند، و client همان step-up موجود را اجرا و یک‌بار retry می‌کند. بنابراین صرف
  نمایش دکمه هرگز مجوز ثبت credential ماندگار نیست.
- **LB-B41 تشخیص و اصلاح شد:** `reauth/options` در نشست منقضی همان وضعیت را به‌صورت ۴۰۴ پنهان
  می‌کرد، در حالی‌که `/api/auth/session` و client step-up قبلاً قرارداد ۴۰۱ داشتند. مسیر options و
  verify اکنون فقط پس از تمام گیت‌های موجود، برای نشست ازدست‌رفته ۴۰۱ no-store برمی‌گردانند؛ CSRF،
  origin، ceremony، پنجرهٔ پنج‌دقیقه‌ای و الزام Passkey تغییر نکرده‌اند.
- تست‌ها ۴۰۱ گزینهٔ reauth، انقضای بین options/verify، لغو Passkey، جلسهٔ بدون ورود، خطای سرویس و
  دستیابی route را pin می‌کنند. بررسی مرورگر در ۱۴۴۰، ۱۲۵۹ و ۳۹۰px سرریز root نشان نداد.

### مرحلهٔ ۹ — یادگیری

- **فایل‌ها:** صفحهٔ جدید `learning`، خواندن از جداول یادگیری موجود.
- **کار:** چیدمان `learning.html` با دادهٔ واقعی؛ هر شاخصی که منبع ندارد «در دسترس نیست».
- **وابستگی:** مرحلهٔ ۲ (الگوی KPI و نمودار).
- **معیار پذیرش:** فقط خواندن؛ هیچ نوشتنی روی دادهٔ یادگیری؛ تعریف «آموخته‌شده» از ماژول مشترک
  LB-B35 گرفته می‌شود نه تعریف جدید.
- **تست:** تست خواندن با نقش محدود؛ تست عدم نوشتن.
- **خطر:** چهار تعریف موازی «آموخته‌شده» (نقص باز LB-B35). **کاهش:** مصرف ماژول مشترک.

#### اجرای مرحلهٔ ۹ (candidate؛ در انتظار PR و CI)

- `#learning` اکنون فقط‌خواندنی است و تنها از `GET /api/dashboard/overview` موجود استفاده می‌کند:
  `learners.activeInWindow` یعنی تعداد زبان‌آموزانی که در پنجرهٔ گزارش موجود دست‌کم یک رویداد مرور
  داشته‌اند. این عدد، تعریف پیشرفت، نگه‌داشت، کیفیت یا روز یادگیری نیست.
- مدل خواندنیِ مجاز برای دقت، نگه‌داشت، دشواری کارت، زمان‌بندی یا توزیع سطح وجود ندارد؛ هر کدام به
  صورت «در دسترس نیست» نمایش داده می‌شود، نه صفر یا دادهٔ prototype.
- هیچ API، grant، migration، SQL، import از `packages/learning-engine` یا منطق scheduler به Admin
  اضافه نشده است. تست مرزی Stage 9 و guard ایستای CP2 برای منع تعریف مستقل اجرا شدند.

### مرحلهٔ ۱۰ — عملیات و تنظیمات

- **فایل‌ها:** `OperationsWorkspace`، `SettingsWorkspace`، `AuditLogWorkspace` و router/sidebar.
- **کار:** چیدمان `ops.html` و `settings.html` با قراردادهای موجود و فقط‌خواندنی. «عملیات» اکنون
  وضعیت پیکربندی پرداخت را فقط از `GET /api/store/payment-config` می‌خواند و گزارش حسابرسی موجود را
  در `#audit` حفظ می‌کند. «تنظیمات» فقط نشست جاری از `GET /api/auth/session` و همان وضعیت پرداخت را
  نشان می‌دهد؛ هیچ input قابل‌ویرایش، mutation، مقدار env یا credential ندارد.
- **داده‌های عمداً unavailable:** uptime/latency، سلامت application/database/storage، queue، log،
  deployment revision، ظرفیت ذخیره‌سازی، وضعیت integrationهای ایمیل/پیامک/رسانه، profile/role و flagهای
  محیطی read model مجاز ندارند. صفحه آن‌ها را نامشخص یا unavailable می‌خواند، نه سالم/ناسالم یا صفر.
- **مرز پرداخت:** endpoint فقط‌خواندنی و credential-safe است؛ حالت‌های `disabled`، `unproven` و `ready`
  از evidence موجود می‌آیند و هیچ activation یا تغییر درگاه اضافه نشده است.
- **معیار پذیرش:** هیچ راه تغییر پرچم یا secret از UI؛ گزارش حسابرسی بدون افت قابلیت فیلتر و با route
  مستقل `#audit` باقی می‌ماند.
- **تست:** سوئیت حسابرسی و تست Stage 10 برای unavailable/expired/error/read-only routes؛ تست اینکه
  تنظیمات هیچ fetch نوشتنی نمی‌فرستد.
- **خطر:** افشای مقدار پیکربندی حساس. **کاهش:** فقط قراردادهای موجود با payload بدون secret مصرف می‌شوند؛
  وضعیت‌های بدون منبع به‌صراحت unavailable هستند.

### مرحلهٔ ۱۱ — Responsive و بازبینی نهایی

- **کار:** چیدمان دسکتاپ/تبلت/موبایل برای همهٔ صفحات، بازبینی RTL، دسترس‌پذیری پایه (فوکوس،
  برچسب‌ها، کنتراست)، و مقایسهٔ نهایی با مرجع.
- **وابستگی:** همهٔ مراحل قبلی.
- **معیار پذیرش:** هیچ صفحه‌ای در عرض موبایل شکسته نیست؛ ناوبری با کیبورد کامل است؛ اختلاف‌های
  باقی‌مانده با مرجع در `DEVIATIONS` به‌روزشده ثبت شده‌اند.
- **تست:** بازبینی دستی در سه عرض + اجرای کامل CI.

## خطرهای سراسری

1. **بازطراحی می‌تواند یک گیت امنیتی را بی‌صدا بردارد.** کاهش: هر PR که فایل احراز هویت یا مسیر
   `support/*` را لمس می‌کند باید تست منفی داشته باشد.
2. **دادهٔ نمایشی prototype می‌تواند وارد محصول شود.** کاهش: `assets/js/data.js` هرگز کپی نمی‌شود؛
   بازبینی هر PR برای عدد hard-coded.
3. **از دست رفتن قابلیت‌هایی که در مرجع تصویر ندارند.** کاهش: فهرست «موجودی» این سند معیار است.
4. **تورم دامنه.** کاهش: هر مرحله یک PR، معیار پذیرش بسته، بدون قابلیت جدید محصول.
5. **استقرار Admin، learner را تحت تأثیر قرار دهد.** کاهش: compose جداگانه، فقط سرویس admin.
