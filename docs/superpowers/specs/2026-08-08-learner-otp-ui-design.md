# طراحی اتصال OTP به ورود اصلی یادگیرنده

## هدف

صفحهٔ ورود اصلی بتواند از مسیر آزموده‌شدهٔ SMS.ir استفاده کند، اما قابلیت در همهٔ محیط‌ها به‌صورت پیش‌فرض خاموش بماند و هیچ انتشار یا دعوتی را فعال نکند.

## تصمیم

یک پرچم عمومیِ غیرحساس به نام `NEXT_PUBLIC_LEARNBOX_OTP_UI_ENABLED` فقط حالت رابط را انتخاب می‌کند. مقدار دقیق `true` رابط OTP واقعی را نمایش می‌دهد؛ هر مقدار دیگر همان نمونهٔ محلیِ صریح را نگه می‌دارد. ارسال واقعی همچنان به پرچم مستقل و سروری `SMS_IR_ENABLED` وابسته است.

منطق مشترک مرورگر برای اعتبارسنجی شماره، خواندن challenge، نگهداری حداکثر سه challenge در حافظه و بررسی پیامک‌های دیررس به `apps/website/lib/otp-client.ts` منتقل می‌شود. صفحهٔ آزمون مالک و ورود اصلی هر دو از همین قرارداد استفاده می‌کنند.

## جریان

1. در حالت محلی، رفتار فعلی بدون درخواست شبکه و با اعلام روشن «کد آزمایشی» حفظ می‌شود.
2. در حالت واقعی، شماره به مسیر هم‌مبدأ `POST /api/auth/otp/request` فرستاده می‌شود.
3. کد پنج‌رقمی با challengeهای همان تب، جدید به قدیم، در `POST /api/auth/otp/verify` بررسی می‌شود.
4. فقط پاسخ دقیق `204` موفق است. پاسخ `400` challenge بعدی را امتحان می‌کند؛ هر پاسخ دیگر متوقف می‌شود.
5. خطای سرویس هرگز به ورود محلی یا پذیرش دلخواه کد تبدیل نمی‌شود.

## امنیت و حریم خصوصی

- شماره، کد و challenge در URL، لاگ یا ذخیره‌سازی مرورگر قرار نمی‌گیرند.
- ساعت مرورگر دربارهٔ انقضا تصمیم نمی‌گیرد؛ سرور مرجع است.
- پرچم رابط هیچ کلید یا دسترسی سروری را افشا نمی‌کند.
- فعال‌سازی production، فهرست دعوت و متن رضایت همچنان نیازمند تأیید مالک است.

## آزمون پذیرش

- حالت پیش‌فرض محلی است و فقط مقدار دقیق `true` حالت واقعی را فعال می‌کند.
- حالت واقعی درخواست و تأیید را از API هم‌مبدأ انجام می‌دهد و نشست HttpOnly موجود را می‌پذیرد.
- `400 → ادامه`، `204 → موفقیت` و `403/503 → توقف` با تست رفتاری پوشش دارند.
- خطای شبکه یا سرویس، `onAuthenticated` را فراخوانی نمی‌کند.
- `pnpm check`، build وب، migration validation و ممیزی production عبور می‌کنند.
