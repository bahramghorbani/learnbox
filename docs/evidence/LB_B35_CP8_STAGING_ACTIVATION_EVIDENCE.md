## 2. V1 equivalence with the flag OFF

Discriminating by construction: a **Box-1** card is the only state where V1 and V2 differ
observably (V1 multiplies by 1.8 and stays in Box 1; V2 graduates to exactly 1.0 and enters Box 2).
A Box-2 card **cannot** discriminate, because V1's `remembered` factor is also 1.8.

```
flag OFF: request accepted through the real web path   :: status=200
flag OFF: Box-1 card follows V1 arithmetic (x1.8), NOT GR-1.8 graduation
  :: 0.0416666667 -> 0.07500000006 (V1 expects 0.07500000006, V2 would give 1)
flag OFF: V2 graduation did NOT happen (card stays in Box 1) :: box=1
flag OFF: event written with engine_version NULL (V1 provenance)
flag OFF: binary response still recorded (CP4/0023 column in use) :: response=known
```

## 5. Fail-closed, transient, client and queue — 24/24

| Logout / session expiry                                 | `pendingCount=1 sessionEnded=true` — nothing lost                              |
| Flag OFF + missing `0023`                               | V1 path unaffected                                                             |

Temporary DDL is applied and restored through `withTemporaryDdl`, which restores in a `finally`
block, so a failed assertion cannot leave the schema misleading: `ddl_apply=2 ddl_restore=2`, and
restoration is itself asserted (`engine_version present=true`).

Two anti-vacuity guards exist because their absence previously produced passing-but-meaningless
assertions:

- the transient test asserts the injected fault was **actually invoked** (`stub_called=true`) —
  overriding the wrong dependency key had silently let a real `200` write through;
- the queue fixture is asserted to load as a valid persisted queue (`loaded=1`) before anything is
  concluded from it — a fixture missing `nextAttemptAt` is discarded as corrupt, which had made the
  earlier queue assertions vacuous.

The only stub in the package is the injected `submit` for the transient case, because the behaviour
under test is the HTTP boundary's error classification. Everything else runs through the real route
handler, runtime wiring, service, engine and Postgres over TLS.

## 6. Rollback rehearsal — 13/13

```
rollback: the V2 write is genuinely V2 (Box-1 graduates to exactly 1.0, V1 cannot do this)
rollback: new writes are accepted again with the flag OFF  :: status=200
rollback: post-rollback arithmetic is self-consistent with V1 (NON-discriminating: V2 from
  stability 1.0 yields the same 1.8; see the Box-1 check below for discrimination)  :: 1 -> 1.8
rollback: the post-rollback event has engine_version NULL (V1 provenance)
rollback: DISCRIMINATING — fresh Box-1 card follows V1 (x1.8) and does NOT graduate
  :: 0.0416666667 -> 0.07500000006 (V1 expects 0.0750000001, V2 would give 1.0 and Box 2); box=1
rollback: the discriminating post-rollback event is also stamped V1 (engine_version NULL)
rollback: no existing event row is rewritten (V2-stamped row count unchanged)
rollback: prior history (incl. response + engine_version) is byte-identical
rollback: MEASURED — stability accumulated under V2 is retained after rollback
  :: actual=1.800000 vs V1-only path=0.135000 (residue=+1.665000 days, box 1 -> 2)
```

**The measured one-way consequence:** turning the flag off restores the V1 _algorithm_ for new
writes; it does **not** restore pre-V2 _scheduling state_. A card that graduated under V2 holds
1.8 days where a V1-only path would have left 0.135 days — a residue of **+1.665 days**, and the
card sits in Box 2 instead of Box 1.

The previous package asserted `retained >= v2Stability`, which is trivially true because the
following V1 write multiplies by 1.8. That is replaced by the comparison above against an
independently computed counterfactual V1-only path, which can actually fail.

## 9. New findings

- **N1 (low, non-blocking, pre-existing).** `LEARNBOX_BINARY_REVIEW=true` against a **pre-0023**
  database returns `503`, because the event INSERT names `response`, which only exists after 0023.
  Isolated by direct comparison (`false`→200, `true`→503). Not a Scheduler V2 defect — it is a
  CP5-era ordering constraint with no preflight of its own. Production sets neither flag.
  **Operational rule for any future cutover: apply `0023` before enabling binary review.**
- **N2 (low, non-blocking).** `createSchedulerV2Preflight` memoises a _successful_ preflight for the
  process lifetime (a failure is never cached). If the 0023 surface disappears **after** a success,
  the next write fails inside the INSERT and is classified `503` (retryable) rather than the
  deterministic `422`. Measured: nothing persisted, and the next request returns `200` once the
  schema is restored, with no restart. A classification imperfection in an abnormal state, not a
  data-integrity defect. Recorded, not fixed — fixing it would mean changing product code, which is
  outside CP8's scope.

## 10. Limitations / not proven

- **Web only.** The Dart/native client was not activated and is **not** covered. Scheduler V2 is
  **not** ready for native: `apps/mobile/.../http_review_sync_transport.dart` still maps any
  non-200 to a retryable failure, so a deterministic `422` would be retried indefinitely. This
  remains a hard blocker for native activation (owner constraint D16).
- Synthetic fixtures on a Production-**shaped** schema built from the repository migration path —
  not a restored copy of Production data.
- Driven in-process through the real route handler, not over the network through a Caddy/systemd
  deployment.
- `card_schedules.state` is still written as a non-authoritative compatibility column; its
  retirement is explicitly out of CP8 scope.
- N1 and N2 are recorded, not fixed.
- The sweep injects boundary stabilities directly (§4), so it proves boundary _handling_, not that
  V2 generates those exact values.
